# 云服务器部署手册

> 面向单机部署（一台 ECS / 轻量应用服务器）。本机演示见 `README.md` 的「Docker 全栈一键起」。
> 需要集群、K8s、多副本的话本手册不覆盖 —— 那要先解决 Redis Pub/Sub 的跨实例广播与向量库的共享问题。

## 最快路径（只演示、不上域名）

要走这条路，**跳过 §0 的域名/HTTPS 与 §5**，其余按 §1 → §4 做完即可：

```bash
# 1) 服务器装 Docker（§1）
# 2) 上传代码 + 两个数据文件（§2、§3 路径 A）
# 3) .env 填 JWT_SECRET / DEEPSEEK_API_KEY / SILICONFLOW_API_KEY（§2）
# 4) 启动
docker compose --profile full up -d --build
# 5) 还原向量 + 验收（§5）
```

**只需在阿里云控制台安全组放行一个端口**：`8081`（演示用；正式上线才换成 80/443 + 域名）。
然后浏览器访问 `http://<公网IP>:8081`。

> 这样做的代价：**HTTP 明文、无域名**。够毕设演示，但**微信小程序正式环境走不通**（强制 HTTPS + 已备案域名）。
> 内存小于 4G 的机器还要按 §0 的说明裁掉监控容器。

## 0. 前置准备

### 服务器规格

| 项 | 建议 | 说明 |
|---|---|---|
| CPU / 内存 | **2 核 4G 起步，推荐 4 核 8G** | 同时跑 MySQL + PG + Redis + 后端 JVM + nginx + Prometheus + Grafana |
| 系统盘 | ≥ 40G | 镜像本身约 2G，另加数据与日志 |
| 系统 | Ubuntu 22.04 / 24.04 或同版本 Debian | 本手册命令按 Ubuntu 写 |
| 带宽 | ≥ 3Mbps | 首次 `docker compose build` 要拉镜像与 Maven/Node 依赖 |

**如果只演示、不做长期服务**：2 核 4G 也能跑起来，但要在 `.env` 里把 `JAVA_OPTS` 压到
`-Xms128m -Xmx512m`，并考虑不启动 Prometheus/Grafana（去掉 `--profile full` 里的监控服务，
或直接只用 `docker compose --profile full up -d backend frontend mysql postgres redis`）。

**如果只有 2G 内存**（免费试用常见规格）：**必须先裁容器再启动**，否则会被 OOM Killer 杀。
在服务器上先 `free -h` 确认，然后：

```bash
# 只起 5 个必需的（放弃 prometheus / grafana）
docker compose --profile full up -d --build backend frontend mysql postgres redis
```

`.env` 里同时压小 JVM 堆（`JAVA_OPTS=-Xms128m -Xmx512m`）。监控看板在演示里讲 `docs/压测报告.md`
的数字即可，不必现场开着。

### 域名与备案（中国大陆节点必读）

- **只演示**：用 `http://<公网IP>:8081` 即可，不需要域名。
- **要正式对外**：大陆节点需要 **ICP 备案**（约 1~3 周），备案前 80/443 会被拦。
- **要演示微信小程序**：小程序正式环境**强制 HTTPS + 已备案域名**，用 IP + 端口走不通
  （开发者工具里可以勾「不校验合法域名」连本机，但那只是开发态）。

### 安全组 / 防火墙

只放行这两个端口，其余一律关闭：

| 端口 | 用途 |
|---|---|
| 22 | SSH（建议限制来源 IP） |
| 80 / 443 | Web（配了 HTTPS 就只放 443） |

**绝不要对公网开放**：3306(MySQL)、5432(PG)、6379(Redis)、9090(Prometheus)、9091(actuator)、3000(Grafana)。
容器之间走 Docker 内网，不需要公网可达。Grafana 如果要在本机看，用 SSH 隧道：

```bash
ssh -L 3000:localhost:3000 user@<服务器IP>     # 然后本机访问 http://localhost:3000
```

## 1. 安装 Docker

```bash
curl -fsSL https://get.docker.com | sh
sudo systemctl enable --now docker
sudo usermod -aG docker $USER    # 之后重新登录，免 sudo
docker compose version           # 确认 compose v2 可用
```

> 国内节点如果拉镜像慢，配置镜像加速（写入 `/etc/docker/daemon.json` 后 `systemctl restart docker`）：
> ```json
> { "registry-mirrors": ["https://docker.m.daocloud.io"] }
> ```

## 2. 上传代码并配置环境变量

```bash
git clone <你的仓库> /opt/rag-customer-system   # 或用 scp/rsync 上传
cd /opt/rag-customer-system
cp .env.example .env
vi .env
```

**`.env` 里必须改的三项**：

```ini
JWT_SECRET=<用 openssl rand -base64 48 生成，长度 >= 32>
DEEPSEEK_API_KEY=sk-...
SILICONFLOW_API_KEY=sk-...
```

**顺手改掉的两项**（默认值只适合本机）：

```ini
MYSQL_ROOT_PASSWORD=<换成强口令>
MYSQL_PASSWORD=<与上面一致>
POSTGRES_PASSWORD=<换成强口令>
GRAFANA_PASSWORD=<换成强口令>
```

> ⚠ `.env` **不要提交进 git**（`.gitignore` 已经排除）。它等价于整套系统的钥匙。

## 3. 准备初始化数据

先想清楚属于哪种情形 —— **两者差别很大，选错会导致「页面能开但一条都搜不到」**：

| | 路径 A：迁移本机数据（**推荐**） | 路径 B：全新空库 |
|---|---|---|
| 适用 | 本机已有知识库，想让云端和本机一致 | 从零开始，知识后面再导 |
| 知识片段 | 159 条直接带过去 | 0 条，需重新采集/导入 |
| embedding 费用 | **不产生** | 每条片段都要重新向量化（花钱） |
| 耗时 | 传输约 10 MB | 重新采集 + 向量化 |

### 路径 A：迁移本机数据

**需要搬两样东西，缺一不可。**

| 数据 | 在哪 | 大小 |
|---|---|---|
| 业务数据（`knowledge_chunk` 159 条、账号、会话、消息） | 本机 MySQL 转储 | ~7.3 MB |
| **向量数据**（`vector_store`） | **本机 PostgreSQL** | ~2.2 MB |

> ⚠ **最容易漏的一环**：向量**不在** MySQL 转储里。只迁 MySQL 的话，片段行会声称
> `vector_status=1`，但 PG 里没有对应向量 → **检索一条都返回不了**，看着像系统坏了。
> 两边的 `knowledge_chunk.vector_id` ↔ `vector_store.id` 必须一一对应。

**A1. 本机导出两个文件**（Windows PowerShell，本机全栈运行中）：

```powershell
cd E:\rag-customer-system

# ① MySQL 业务数据（确认是最新的；不是就重跑 export-mysql.ps1）
pwsh tools\docker\export-mysql.ps1

# ② 向量数据 —— 用 --data-only！
docker exec rag-postgres sh -c 'pg_dump -U postgres -d rag_vector --data-only --table=vector_store --no-owner --no-acl > /tmp/vs_data.sql'
docker cp rag-postgres:/tmp/vs_data.sql .\tools\docker\initdb\02_vector_store_data.sql
```

> **为什么用 `--data-only`**：`vector_store` 表结构（含 HNSW 索引）由**应用启动时自动创建**，
> 不需要从本机搬。只导数据的好处是迁移与「源库的索引状态」解耦 —— 万一源库有索引冗余
> （见 §8），也不会把它一起搬到服务器。整表 dump 会连 `CREATE INDEX` 语句一起带过去。

**A2. 上传到服务器**：

```bash
scp tools/docker/initdb/01_rag_customer.sql      root@<IP>:/opt/rag-customer-system/tools/docker/initdb/
scp tools/docker/initdb/02_vector_store_data.sql root@<IP>:/opt/rag-customer-system/tools/docker/initdb/
```

> ⚠ `tools/docker/initdb/*.sql` 在 `.gitignore` 里（含真实业务数据），**不会随 `git clone` 过来** ——
> 必须手动上传这两个文件。

**A3. 之后怎么走**：`01_rag_customer.sql` 会在 MySQL 容器**首次启动时自动执行**（见 §4）；
向量数据要等**应用启动、自建完 `vector_store` 表之后**再灌（见 §5）。

### 路径 B：全新空库

```bash
cp src/main/resources/schema.sql tools/docker/initdb/01_schema.sql
```

`schema.sql` 自带建表 + 种子数据（知识分类、角色权限、演示账号），
`DataInitializer` 会在应用启动时补齐 demo 账号口令与角色绑定。

> **知识库数据要另外导入**：`schema.sql` 只建表、不含知识片段。
> 用管理后台「知识库管理 → 导入 CSV」，或走 `tools/kb_oneclick.ps1` 的完整流程。
> 片段导入后要等向量化完成（`vector_status=1`）问答才有效 —— 这条路**每条片段都会产生 embedding 费用**。

## 4. 启动

```bash
# 预检（.env / 密钥 / 初始化脚本 / 端口）—— 有 PowerShell 环境时用这个最稳
# 纯 Linux 环境可跳过，直接看下一步
docker compose --profile full up -d --build
```

首次构建要下载 Maven 与 Node 依赖，**约 5~15 分钟**（取决于带宽）。看进度：

```bash
docker compose --profile full logs -f backend
```

起来后验证：

```bash
curl -s http://localhost:8081/api/rag/hello
# → {"code":200,"message":"success","data":"Hello RAG"}
```

**注意**：镜像是构建出来的（后端 jar + 前端静态产物），所以
**每次改代码都要 `docker compose --profile full up -d --build`** 重建，不会自动热更新。

## 5. 还原向量数据（仅路径 A）+ 迁移验收

> 走**路径 B（全新空库）**的跳过本节，直接到 §6。

### 5.1 还原向量

**必须在应用起来之后做**：`vector_store` 表由 Spring AI 在**应用启动时自动创建**，
早于启动灌数据会因为表不存在而失败。

```bash
cd /opt/rag-customer-system
docker exec -i rag-postgres psql -U postgres -d rag_vector < tools/docker/initdb/02_vector_store_data.sql

# 重启后端：重建 BM25 语料、刷新连接池
docker compose --profile full restart backend
```

### 5.2 验收：四条全过才算迁移成功

```bash
# ① 接口活着
curl -s http://localhost:8081/api/rag/hello
#   → {"code":200,"message":"success","data":"Hello RAG"}

# ② ★ 关键判据：片段数必须等于向量数
docker exec rag-mysql sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -N -e "SELECT COUNT(*) FROM rag_customer.knowledge_chunk WHERE deleted=0 AND vector_status=1;"'
docker exec rag-postgres psql -U postgres -d rag_vector -t -c "SELECT COUNT(*) FROM vector_store;"
#   → 两者应相等（本机迁过来是 159 / 159）

# ③ 走一次完整问答链路
curl -s -X POST http://localhost:8081/api/chat/ask \
  -H 'Content-Type: application/json' -d '{"message":"2026 本科新生入学须知"}'
#   → answer 有内容、sources 非空、正文句尾带行内引用 [n]

# ④ 三个演示账号都能登录
curl -s -X POST http://localhost:8081/api/auth/login \
  -H 'Content-Type: application/json' -d '{"username":"admin","password":"Admin@Ysu2026"}'
```

**若 ② 两边不相等** —— 几乎总是「只灌了 MySQL、没灌向量」。补救就是重跑 5.1 再验一次。

> 也可以直接跑项目自带的一键验证（需要服务器上有 pwsh 与 Python，一般没有，可跳过）：
> `pwsh tools/verify_all.ps1 -SkipDemo`

## 6. 配 HTTPS

### 方式 A：certbot（推荐，免费自动续期）

先让 nginx 之外的 80 端口空出来（certbot 要用 80 做验证）。最简做法是**用宿主机的 nginx 或 Caddy
反向代理到容器的 8081**，而不是改容器内的 nginx：

```bash
sudo apt install -y nginx certbot python3-certbot-nginx
sudo tee /etc/nginx/sites-available/rag <<'EOF'
server {
    listen 80;
    server_name your.domain.com;
    location / {
        proxy_pass http://127.0.0.1:8081;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        # SSE 必须关缓冲，否则「流式」会变成整段一次性返回
        proxy_buffering off;
        proxy_read_timeout 300s;
    }
    location /ws/ {
        proxy_pass http://127.0.0.1:8081;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_read_timeout 3600s;
    }
}
EOF
sudo ln -s /etc/nginx/sites-available/rag /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
sudo certbot --nginx -d your.domain.com
```

certbot 会自动改写成 443 并配置续期 timer，验证：`sudo certbot renew --dry-run`。

### 方式 B：云厂商证书

在控制台申请免费证书，下载 nginx 版，把 `.pem` / `.key` 放到服务器并挂载进容器，
在 `frontend/nginx.conf` 里加 443 server 块（注意：容器要映射 443，且 SSE 的
`proxy_buffering off` 与 `/ws/` 的 Upgrade 头一个都不能少）。

### 配好 HTTPS 之后

- 前端**不需要重新构建**：它全程用相对路径（`/api`、`${location.host}/ws/...`），换域名不用改代码。
- 但 **Android 端与小程序的 `BASE_URL` 是编译期内联的**，换域名要改 `config.ts` / `BuildConfig`
  后重新构建，否则仍指向旧地址。

## 7. 备份

### MySQL（业务数据：用户、会话、消息、知识片段元数据）

```bash
# 每天凌晨 3:10 全量备份，保留 14 天
cat > /etc/cron.d/rag-mysql-backup <<'EOF'
10 3 * * * root docker exec rag-mysql mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --single-transaction --default-character-set=utf8mb4 --databases rag_customer | gzip > /opt/backup/rag_customer_$(date +\%F).sql.gz && find /opt/backup -name 'rag_customer_*.sql.gz' -mtime +14 -delete
EOF
mkdir -p /opt/backup
```

> cron 里读不到 `.env`，把口令写进脚本或用 `--defaults-extra-file` 更稳妥。

### PGVector（向量数据）

向量是**可以重建的**（`POST /api/knowledge/chunk/{id}/reindex`），但重建要重新调 embedding
（花钱、花时间），所以还是备份：

```bash
docker exec rag-postgres pg_dump -U postgres rag_vector | gzip > /opt/backup/rag_vector_$(date +%F).sql.gz
```

或者对 Docker volume 做快照（云厂商的磁盘快照更省事）：
`docker run --rm -v rag-customer-system_pg-data:/data -v /opt/backup:/backup alpine tar czf /backup/pg-data.tar.gz -C /data .`

### 恢复

```bash
gunzip -c /opt/backup/rag_customer_2026-09-12.sql.gz | docker exec -i rag-mysql mysql -uroot -p
gunzip -c /opt/backup/rag_vector_2026-09-12.sql.gz | docker exec -i rag-postgres psql -U postgres -d rag_vector
```

## 8. 故障排查

| 现象 | 排查 |
|---|---|
| `docker compose up` 报端口占用 | `ss -lntp \| grep <端口>`；8080/8081 常被别的服务占；改 `.env` 里的 `WEB_PORT` |
| 页面能开但接口 502 | 看 `docker compose logs backend`；多半是 MySQL/PG 还没 healthy，或 `.env` 里密钥为空 |
| 登录一直失败 | `JWT_SECRET` 为空或不足 32 字符；或 `DataInitializer` 还没跑完（看后端启动日志） |
| 问答报鉴权错 | `DEEPSEEK_API_KEY` / `SILICONFLOW_API_KEY` 没配或额度用尽 |
| 「流式」变成一次性整段出现 | **反向代理没关缓冲**。nginx 加 `proxy_buffering off`；云厂商的 SLB/CDN 也要关（有些 CDN 会强制缓冲 SSE，此时只能绕开 CDN 直连） |
| WebSocket 连不上 | 反代缺 `Upgrade` / `Connection: upgrade` 头；或用 HTTPS 时前端自动走 `wss`，证书必须是有效的 |
| 内存告警 / 容器被杀 | 后端调小堆：`.env` 里 `JAVA_OPTS=-Xms128m -Xmx512m`；MySQL 调 `--innodb-buffer-pool-size` |
| 向量检索没有结果 | `SELECT COUNT(*) FROM knowledge_chunk WHERE deleted=0 AND vector_status=1`；若为 0，说明知识片段没导入或向量化失败，走「知识库管理 → 重建向量」 |
| Grafana 看板空白 | Prometheus 没抓到：`docker compose logs prometheus`，确认 targets 里 `backend:9091` 是 UP |
| **向量写入很慢 / PG 磁盘占用异常** | `vector_store` 上累积了**冗余 HNSW 索引**。自查：`docker exec rag-postgres psql -U postgres -d rag_vector -c "SELECT count(*) FROM pg_indexes WHERE tablename='vector_store';"` —— **正常应为 2**（1 个主键 + 1 个 HNSW）。**根因已修**（`PgVectorConfig` 改为 `PgIndexType.NONE` + 启动时 `CREATE INDEX IF NOT EXISTS`；Spring AI 0.8.1 原本执行的是无索引名、无 `IF NOT EXISTS` 的 `CREATE INDEX`，导致每次启动新增一个，实测 +2/次、一度累积到 223 个占 341 MB）。**老实例的存量冗余**用 `docker exec -i rag-postgres psql -U postgres -d rag_vector < tools/db/pg-vector-index-cleanup.sql` 清理（幂等，清理后索引占用从 341 MB 降到 1.3 MB） |

## 9. 退化方案：不容器化

如果服务器上已有 MySQL/PG/Redis，或不想承担镜像维护成本，可以只跑后端与前端：

```bash
# 后端：打成 jar 后由 systemd 托管
mvn clean package -DskipTests
sudo tee /etc/systemd/system/rag-backend.service <<'EOF'
[Unit]
Description=RAG Customer System Backend
After=network.target

[Service]
User=www-data
WorkingDirectory=/opt/rag-customer-system
EnvironmentFile=/opt/rag-customer-system/.env
Environment=SPRING_PROFILES_ACTIVE=prod
ExecStart=/usr/bin/java -Xms256m -Xmx768m -jar /opt/rag-customer-system/target/rag-customer-system-0.0.1-SNAPSHOT.jar
Restart=always
RestartSec=10

[Install]
WantedBy=multi-user.target
EOF
sudo systemctl daemon-reload && sudo systemctl enable --now rag-backend

# 前端：npm run build 后把 dist 交给宿主机 nginx 托管，反代 /api 与 /ws 到 127.0.0.1:8080
```

这种形态下 `application-prod.yml` 要把 `localhost` 换成实际库地址，口令全部走环境变量。

## 10. 上线检查清单

- [ ] **（路径 A 迁移）片段数 = 向量数**：§5.2 的第 ② 条，两个 `COUNT(*)` 相等（应均为 159）
- [ ] **（路径 A 迁移）真问过一句**：§5.2 的第 ③ 条，答案有内容且带行内引用 `[n]`
- [ ] `.env` 里 `JWT_SECRET` 是随机值（不是仓库默认的 `local-dev-...`）
- [ ] MySQL / PG / Grafana 口令都换成了强口令
- [ ] 安全组只开了必要端口：**正式上线 = 22 / 80 / 443**；**纯演示 = 22 / 8081**
- [ ] `docker compose --profile full ps` 全部 `healthy`（或 `Up`）
- [ ] `curl http://<地址>:8081/api/rag/hello`（或配了 HTTPS 后用域名）返回 200
- [ ] **PG 索引没膨胀**：`SELECT count(*) FROM pg_indexes WHERE tablename='vector_store';` 应为 **2**（§8 有清理办法）
- [ ] 反代关掉了 `proxy_buffering`，SSE 是真流式（前端能看到逐段出现）
- [ ] WebSocket 能连（客服工作台空白页能收到推送）
- [ ] 备份 cron 已就位，且**手工跑过一次恢复演练**
- [ ] Grafana 看板有数据（Prometheus targets 全 UP）
- [ ] 演示账号口令已改：`.env` 里设 `DEMO_ADMIN_PASSWORD` / `DEMO_AGENT_PASSWORD` / `DEMO_USER_PASSWORD`，
      并确认 `DEMO_RESET_PASSWORDS=false`（否则重启会把口令改回 .env 里的值）；
      或直接停用 demo 账号
- [ ] **改配置或代码后必须 `docker compose --profile full up -d --build`** ——
      只 `up -d` 会用旧镜像，容器里跑的还是老配置（这一点实测踩过：改了 `application.yml`
      却只 `up -d`，容器行为完全没变，排查了很久）
