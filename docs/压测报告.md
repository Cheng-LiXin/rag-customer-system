# 压测报告（JMeter 阶梯压测）

> 数据由 `tools/loadtest/run.ps1` 跑出，明细在 `tools/loadtest/results/*.jtl`。
> 压测脚本与命令见 `tools/loadtest/`；本文件只解释**结果与口径**。

## 1. 压测口径（先讲清楚，否则数字是废的）

| 轮次 | 打的是什么 | 测什么 | 为什么不这样打就没意义 |
|---|---|---|---|
| **A 轮** | 已预热过的同一批问题（命中 `qa:cache`） | **服务端并发能力** | 缓存命中路径不调大模型，这才是"系统吞吐"的合理口径；否则测的是 DeepSeek 的排队 |
| **B 轮** | 换一批没问过的问题（清空 `qa:cache:*`） | **真实端到端时延** | 走完整链路：检索 + 拒答判定 + 抽句 + 大模型 + 拼装 |

**为什么 B 轮只敢用 5 并发**：冷路径每次都要调 DeepSeek。并发一高就撞上游限流，
延迟数据会变成"排队时间"而不是"系统处理时间"——**100 并发打冷路径得到的是废数据，
而且烧钱**。这一点在脚本里也做了提醒。

三个轮次的参数：

```powershell
pwsh tools\loadtest\run.ps1 -Warmup -Loops 48                      # 预热（强制单线程）
pwsh tools\loadtest\run.ps1 -Tag A -Threads 20 -Ramp 60 -Loops 5   # A 轮
docker exec rag-redis redis-cli EVAL "...del qa:cache:*..." 0      # 清缓存
pwsh tools\loadtest\run.ps1 -Tag B -Threads 5 -Ramp 15 -Loops 5    # B 轮
```

## 2. 结果

### A 轮：缓存路径（20 线程 / 爬升 60s / 每线程 5 次 = 100 请求）

| 指标 | 值 |
|---|---|
| 样本数 | 100（成功 100，**错误率 0.00%**） |
| 吞吐 | 1.7 TPS（受 60s 爬升支配，非系统上限） |
| 响应时间 | **p50 11ms · p90 20ms · p95 22ms · max 246ms** |

### B 轮：冷路径（5 线程 / 爬升 15s / 每线程 5 次 = 25 请求）

| 指标 | 值 |
|---|---|
| 样本数 | 25（成功 25，**错误率 0.00%**） |
| 吞吐 | 1.6 TPS（受爬升与上游限流支配） |
| 响应时间 | **p50 1090ms · p90 1412ms · p95 1465ms · max 1743ms** |

### 对照：混合轮（20 线程 × 50 循环 = 1000 请求，缓存从冷到热）

这一轮是最直观的一张图 —— 跑的过程中缓存逐步填满：

| 阶段 | 累计样本 | 平均响应 | 说明 |
|---|---|---|---|
| 前 10 次 | 10 | **944ms** | 冷路径（首批问题没缓存） |
| 此后 623 次 | 633 | **82ms** | 缓存命中 |
| 最后 367 次 | 1000 | **13ms** | 缓存全部命中 |

整轮：1000 请求 / **0 错误** / p50 10ms / p95 676ms / max 1596ms。

## 3. 结论

### 缓存的效果是数量级的

冷路径 p95 **1465ms** → 缓存路径 p95 **22ms**，**快了约 66 倍**。
这印证了 `qa:cache`（键 `qa:cache:{MD5(问题)}`，TTL 3600s）的设计目标：
**校园客服的问题高度重复**（"什么时候报到""校园卡怎么补办"），热点问题一旦被问过，
后续几乎零成本。

### TTFT 目标判定：达标，但要说清口径

文档要求 **TTFT < 1.5s**。实测：

| 来源 | p50 | p95 | max |
|---|---|---|---|
| 压测 B 轮（冷路径，25 样本） | 1090ms | **1465ms** ✅ | 1743ms |
| 150 题离线评估（冷路径） | 1070ms | 1675ms | 2648ms |

**达标（p50/p95），但 max 会超线。**

原因必须如实说：本项目的 SSE 是**伪流式** —— 答案在 `Flux` 创建**之前**就已整段算出，
分片之间也没有延迟，所以「首片 token 到达时间」≈ 全链路耗时。
这个数就是**检索 + 拒答判定 + 一次大模型抽句 + 拼装**的端到端时间，
其中**上游大模型占绝对主导**（检索本身只有几十毫秒，见下表）。

### 瓶颈分析

| 环节 | 量级 | 依据 |
|---|---|---|
| 向量检索（PGVector + bge-m3 查询向量） | 数十毫秒 | 检索预览接口单次调用 ~30-60ms |
| 拒答判定 / 防护三层 | < 1ms | 纯内存正则，且拒答命中时**直接省掉整个大模型调用** |
| **大模型抽句（DeepSeek）** | **~1s** | 冷路径 p50 1090ms 减去上述环节 |
| 答案拼装 + 落库 | 数毫秒 | — |

**结论：瓶颈在上游大模型，不在本系统。** 要再压 TTFT，可行的方向是：

1. **提高缓存命中率**（最有效、零成本）—— 热点问题前置预热，或把 TTL 从 1h 拉长；
2. **超纲问题早退**：拒答阈值命中时**不调大模型**，实测超纲题 TTFT 显著低于正常题；
3. **降 `rag.top-k`**（当前 3）：候选片段少了，抽句提示词短了，但会牺牲召回 —— 需用评估集回归验证。

不宜做的：为了压 TTFT 而把答案改成"边检索边流式吐"，那会破坏抽取式回答"整段逐字拼装"的前提。

## 4. 局限与没做的事

- **没有做更大并发的拐点测试**：冷路径受上游限流，A 轮的 TPS 又被 60s 爬升支配，
  所以本报告**不给"系统最大吞吐"这个数** —— 给了也是假的。
  真要测服务端上限，应该只在缓存路径上逐步加压（`-Threads 20/50/100 -Ramp 10`），
  用 `rag.qa.answers{result="cached"}` 指标看拐点。
- **单机单实例**：没有多副本、没有分布式压测机，所以数据只反映单机表现。
- **上游时延波动**：DeepSeek 的响应时间本身有较大方差（max 1743ms vs p50 1090ms 就是这个来源），
  样本量 25 也偏小。要更稳的结论需要多轮重复取分布。
