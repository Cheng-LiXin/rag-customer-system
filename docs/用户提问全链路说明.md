# 用户提问 → 系统回答：背后发生了什么

> 本文按「用户在对话框敲下一句话」到「屏幕上逐字打出答案」的真实调用顺序讲。

---

## 0. 一句话概括

用户在对话框里发一句话，前端用 **SSE** 把问题送到后端；后端**先查缓存、再走一轮确定性 FAQ 短路**（省钱、防串答），都没命中才去
**向量化 → 检索 Top-K → 让大模型只挑「原文行号」→ Java 按行号逐字拼回原文**，顺手落库、异步回写缓存，最后把答案切片当 token 推回前端打字机渲染。

关键点：**大模型全程不造句**，只做「选哪些原文句子 / 怎么分组」，所以答案永远忠于知识库、不会出现语序错乱或数字幻觉。

---

## 1. 分步详解

### ① 前端：把问题发出去

- 入口在 `frontend/src/views/ChatHome.vue:368` 的 `streamAsk()`，它调用 `frontend/src/api/chat.ts:11` 的 `streamUrl()` 拼出
  `GET /api/chat/stream?message=…&conversationId=…`，用 `fetch` + `Accept: text/event-stream` 消费，登录时带上 `Authorization: Bearer <JWT>`。
- 后端入口 `ChatController.stream()`（`src/main/java/com/rag/controller/ChatController.java:56`）返回 `Flux<String>`——注意**不是 `ServerSentEvent`**，
  所以前端解析要同时兼容 `data:` 前缀行和裸 JSON 行两种。
- 另有普通（非流式）接口 `POST /api/chat/ask`（`ChatController.java:44`），走同一套核心逻辑，只是不推流。

### ② 后端：两级「短路」，先花钱之前先省钱

进 `ChatServiceImpl.ask()/stream()`（`src/main/java/com/rag/service/impl/ChatServiceImpl.java:178` / `:214`）后，在做任何昂贵操作前有两道闸：

1. **问答缓存**（`ChatServiceImpl.java:180`）：键 `qa:cache:{MD5(问题)}`，命中直接返回并标 `fromCache=true`，**连向量检索都不做**。TTL 默认 3600s（`rag.cache.ttl-seconds`）。
2. **确定性 FAQ 短路**（`:189`，实现 `faqAnswer()` 在 `:275`）：把问句剥掉标点空白得「核心串」，**只有长度 ≤12 字**才判定，避免抢走真实问题。
   命中问候 /「你是谁」/「你可以做什么」/「怎么使用」这类上手问法就回固定文案（`FAQ_GREET`/`FAQ_WHO`/`FAQ_CAN`/`FAQ_HOW`），**不检索、不调模型**。

   > 为什么要这道闸：泛问句（如「你可以做什么」）走 RAG 时，通用词会把校园生活类原文（浴池圈存、班车预约）一起召回，答出与助手无关的内容。

命中任一道闸 → 直接跳到第 ⑤ 步（仍然正常落库、正常走缓存）。

### ③ 检索：查询向量化 + Top-K

- `retrieve()`（`:264`）调 `vectorStore.similaritySearch(...withTopK(3))`，`rag.top-k` 默认 3。
  向量由 **SiliconFlow `BAAI/bge-m3`（1024 维）**生成，存 PostgreSQL + pgvector（COSINE）。
- 命中的片段会顺手 `incrementHitCount()`（`:311`）累加 `hit_count`，这是后台「热门知识 Top10」的数据来源。
- 注意：**向量化只用切片正文 `content`，标题不进向量**，标题只放 metadata 供展示与统计。

### ④ 生成：让模型「只选编号」，Java 拼原文（本项目最关键的设计）

`answer()`（`:346`）分 A / B 两路：

**A 路（默认开，`rag.structured.enabled=true`）**
- `planBullets()`（`:540`）把片段切成「句元」（竖线表格行整行原子，其余按句末标点切，见 `splitUnits()` `:395`），编号后交给大模型，
  **只让它输出一个 JSON**：`{"groups":[{"t":"小标题","n":[原文行号…]}]}`——不重写、不复述任何事实句。
- `parseGroups()`（`:569`）做容错解析：剥代码块、裁越界编号、去重、限组数（`max-groups` 默认 4）与每组行数（`max-per-group` 默认 4）。
- `renderMarkdown()`（`:645`）按行号**逐字拼回原文**：每组渲染成 `**小标题**` + 若干 `- 原文句`；连续竖线表格行聚成合法 markdown 表格。
- 若某句说「见下表 / 如下 / 如表」而模型漏选了表格，`referencedTableRun()`（`:720`）会把该句之后同一片段里紧邻的整块表格行并进来，**杜绝「具体见下表」悬空**。
- 最后 `withFooter()` → `referenceFooter()`（`:916` / `:929`）按 `chunk_id` 回查 `knowledge_chunk` 的 `source_url/source_title`，
  **按文件去重**后在答案末尾附「参考文件：」链接列表。

**B 路（降级）**：A 路异常 / 输出为空 / 开关关闭时，退回旧版扁平抽取式三档——
① 严格选句（全量）→ ② 收敛到 Top-1 片段再严格选 → ③ 仍空且最相似片段相似度 ≥ `rag.partial-min-score`(0.55) 时走宽松档
（`selectPartial()` `:467`，让模型挑至多 3 句承载实质信息的句子）。仍选不中就回固定文案
`资料中没有相关内容，建议换个问法或补充关键词。`（`:103`）。

> **为什么非要这么绕**：`deepseek-chat` 对含表格噪声的整段长文**逐字复述不稳定**，`temperature=0` 也压不住——同一问题同一参数，
> 前一次干净、后一次语序就乱了。把「生成」降级成「选编号」，就等于把复述能力从关键路径上摘掉了。

**兜底与缓存纪律**：答不上来的否定文案**不写入 `qa:cache`**（`:207`、`:251` 都有这个判断）。否则一次误判会被缓存 1 小时，
后续修好了也会一直命中旧否定。

### ⑤ 落库、回写、推流

- **事务落库** `persistExchange()`（`:804`）：在一个编程式事务里 `ensureConversation()` → 写 1 条 USER 消息（含 `intent_category` 意图分类）
  → 写 1 条 AI 消息（含 `citations` 引用 chunk_id 列表）→ 更新会话 `last_reply_time`。
- `ensureConversation()`（`:839`）的复用规则：优先复用传入的、且 `status=1` 且归属一致的会话；否则复用该用户最近一条进行中的 AUTO 会话；
  都没有才新建。**结束的会话不会被续写**。
- **异步回写缓存**：非否定答案才 `cacheService.put()`（`:208`）。
- **SSE 推流**：`stream()` 把最终答案按 **18 字符一片**切成 `token` 事件（`:245`，`slice()` `:1007`），
  最后补一个 `end` 事件携带完整 `ChatAnswer`（答案 + 参考来源 + 意图 + 会话 id）。**流是「伪造」的**——真正的生成早已一次性完成，
  分片只是为了保留打字机观感。

> ⚠️ **一个必须知道的坑**：SSE 返回 `Flux` 后，响应体在 **Reactor 线程**上异步订阅执行，`SecurityContextHolder`（ThreadLocal）已经不可达，
> 会话会被绑到游客 `userId=0`。所以代码在 **servlet 请求线程**里就先把 `resolveUserId()` 解析好（`:242`），随闭包透传给异步持久化。

### ⑥ 前端渲染

拿到 `end` 事件后，前端用 `MarkdownText.vue`（marked + DOMPurify）渲染 markdown 答案，展示**参考来源**（只展示标题 + 分类 + 相似度，
不渲染正文）与**意图标签**。若用户此时点「转人工客服」，进入下面这套状态机。

## 2. 转人工：会话状态机

**先记住一件事：会话只有两态**——`conversation.status` 的 **1=进行中 / 2=已结束**。
「待处理/处理中/已解决/已关闭」是 **`ticket` 工单表**的四态，跟会话是两套独立体系，别混。

**人工的「排队中 / 已分配」不是数据库状态**，而是 Redis 子状态：

| Redis 键 | 含义 |
| --- | --- |
| `rag:cs:agents` | 当前持有 WebSocket 的在线客服集合 |
| `rag:cs:queue` | 等待接入的用户会话队列（List） |
| `rag:cs:assign` | 会话 → 客服 的分配关系（Hash） |
| `rag:cs:load` | 每个客服的在管会话数（Hash），**选人用** |
| `rag:cs:unread` | 每个会话的未读数（Hash） |

**主链路**（图中 01~05）：

1. **机器人会话** `AUTO/status=1` — 每次提问由 `ensureConversation()` 创建或复用。
2. **转人工** — `POST /api/agent/transfer`（需 JWT）。`resolveHumanConversation()` 决定复用哪条会话：
   传了 `conversationId` 且归属校验通过就**原地把 `session_type` 从 AUTO 升级为 HUMAN**（保留上下文，不另开会话）；
   否则复用该用户最近一条 HUMAN 会话（含已结束的，重新激活）；都没有才新建。
3. **等待接入** — 入 `rag:cs:queue` 排队。`GET /api/agent/queue/{id}` 返回 `position`（已在 `assign` 里则返回 0）。
4. **客服接待中** — 分配成功后写 `rag:cs:assign`、`rag:cs:load +1`、落库 `agent_id`，
   并**双向推 WS** `assigned` 事件给客服和用户。选人逻辑是**最少负载**：遍历在线客服，取在管会话数最少者（缺失按 0 计）。
5. **已结束** `status=2` — **不清 `agent_id`**，保留归属便于回查。

**三条结束路径**：

| 路径 | 触发 | reason | 收尾动作 |
| --- | --- | --- | --- |
| 任一方主动结束 | `POST /api/agent/conversation/{id}/close` | `manual` | 完整收尾（见下） |
| 已分配客服的会话双方 10 分钟无对话 | `ConversationAutoCloseTask` 定时扫描（`rag.human.timeout-minutes`） | `timeout` | 同上 |
| 机器人会话连续 30 分钟无消息 | 同一任务（`rag.session.timeout-minutes`） | 无 | **纯 SQL 置 2**，不发通知、不碰 Redis |

完整收尾（`AgentService.closeConversation(id, reason)`）固定五步：置 `status=2` → 摘 `assign` 并 `load-1`、给客服发 `closed` 事件 →
从 `queue` 移除 → 删 `unread` → 给用户发 `closed` 事件，最后调一次分配（让出负载空位）。

**两条回收边**：

- **客服下线 → 重新入队**：客服 WebSocket 断开时，把 `assign` 里属于他的会话全部**重新 `rightPush` 回 `queue`**，删掉他的 `load` 键，
  再尝试分配给其他在线客服。**注意这条不置 `status=2`**——会话回到「等待接入」，属于可恢复的中断。
- **reopen**：`POST /api/agent/conversation/{id}/reopen` 把已结束会话重新拉回接待中，旧客服 `load-1`、新客服 `load+1`，只给客服推 `assigned`。

**两个容易踩的点**（图中特别标了）：

1. 排队**未接**的会话（`agent_id` 为空）**不会被 10 分钟超时扫到**——`selectStaleHuman` 的 SQL 显式要求 `agent_id IS NOT NULL`，
   避免误杀还在等待的用户。
2. 「机器人静默超时」走的是纯 SQL 批量更新，**没有任何 WS 通知**，用户端不会收到会话已结束的推送。

**满意度评价**在会话结束后提交（`POST /api/satisfaction`，需 JWT）；防刷策略是**同一会话至多一条**：
先按 `conversation_id` 查，存在则更新覆盖，不存在才插入，并用 DB 唯一键 `uk_conversation` 兜住并发首评。

## 3. 为什么要这么设计（答辩可讲的取舍）

| 设计 | 解决的问题 |
| --- | --- |
| 模型只选编号、Java 拼原文 | `deepseek-chat` 长文复述不稳定 → 彻底移除生成侧的复述能力，杜绝语序错乱/数字幻觉 |
| 缓存 → FAQ → RAG 三级短路 | 高频重复问题不重复花钱；泛问句不串答无关资料 |
| 否定答案不入缓存 | 一次误判若被缓存 1 小时，修好后仍会命中旧否定（**踩过**） |
| SSE 先在请求线程解析 userId | Reactor 线程拿不到 ThreadLocal 的 SecurityContext，会把会话绑成游客 |
| 答不上来可转人工 | RAG 覆盖率有上限，人工兜底保证服务不中断 |
| 客服下线不置结束、只回队列 | 断线是**可恢复中断**，不该被当成会话终止 |
